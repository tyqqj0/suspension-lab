# 设计候选与科学边界

状态：2026-10-14 讨论基线。已确认部分以 [requirements.md](requirements.md) 为准；本文件提出的首版方案、数据结构和技术栈，除明确引用已确认需求者外，均为**建议／待确认**。

## 1. 候选总体方案

- Three.js 负责渲染，Rapier 提供刚体／约束求解，自定义悬架与轮胎力律。Three.js 不是物理引擎。
- 首先做七自由度垂向整车：车身浮沉、俯仰、侧倾，四个轮端簧下跳动。简化导向，不逐根复现悬架连杆。
- 这是候选的受控垂向实验模型，不天然具有完整六自由度行驶、转向和极限操控能力；纵向运动／路面输入的实现随实验方式再定。
- 四分之一车数学模型作为物理校核参照，不建立第二套完整产品。
- 外观与物理参数分离：换材质／车壳不应改变实验数值。建议先用自建、整洁的通用 SUV 外观，钛3精确资产不阻塞物理验证；用户尚未确认首版外观取舍。

## 2. Module / Interface / Seam 候选

下列是职责划分，不是已决定的目录、包或需要立即创建的脚手架。

| Module | 小 Interface 应表达的能力 | Implementation 应隐藏的复杂性 |
|---|---|---|
| 动力学 | 实验配置 → 运行 → 带单位的结果 | Rapier 对象、约束、力律、积分步长与状态采样 |
| 实测数据 | 获取／导入采集记录与质量信息 | 平台传感器权限、时间戳来源、坐标转换与缺测 |
| 校准与分析 | 记录＋显式处理配置 → 派生结果 | 过滤、坐标对齐、比较、拟合与不确定性 |
| 展示 | 仿真／实测状态 → 3D 与图表 | 车模资源、渲染、相机；不改变物理状态 |
| 本地存储 | 按稳定标识存取／导出四类资料 | 具体持久化与格式迁移 |

以足够的 Depth 保持调用方简单；测试跨与调用方相同的 Seam。手机采集与文件导入真正并存时再确立 Adapter；不要预建一组只有空实现的抽象层。

### 账号 Interface 的最小预留（待确认）

建议本地数据与身份解耦，核心使用流程无需账号；在未来确需同步／归属时再引入身份或同步 Adapter。本轮只记录扩展点，不实现登录页、鉴权、用户表、服务端或伪账号。稳定 ID 与格式版本服务于数据本身，不要求每份本地数据现在就带远端 userId。

## 3. Rapier 自建物理的实现注意点

以下根据前轮查阅的官方文档记录，正式实现时仍需按选定包版本核对签名与单位。

- 使用基础刚体、关节与施力能力自建车身与轮端；射线车辆控制器无独立簧下质量，不代表 Rapier 基础能力不能建立它们。
- 自定义线性阻尼例：`Fd = -c * v_rel`，其中正方向与相对速度定义须明确；以后可扩展压缩／复原不同的力速关系与控制指令。
- 车身与轮端受等大反向的力；作用点不在质心时产生转矩。全局 rigid-body damping 不是悬架相对运动阻尼。
- `JointData.prismatic`、`JointData.spring` 及运动锁定可作为候选手段，选择前验证其约束、自由度和耗能；不要将关节 motor damping 直接当作已验证的液压减振器。
- 惯量必须有合理物理语义。Rapier 将零角惯量视为对应方向无限惯量，不应以零冒充未知值。
- 硬轮接触仅有接触几何和求解器摩擦，不自动获得轮胎垂向弹性、接触包络或 Pacejka/Fiala；轮胎模型与适用频段需要另定。
- 检查约束是否引入额外自由度或过约束；不要将“车身＋四刚体”直接等同于已验证的七自由度模型。

## 4. 手机采集候选

采集平台选择依赖实际手机与使用场景，而不是先选跨平台框架。切导航后的分阶段交付取舍见 [需求 C2](requirements.md)；锁屏条件与通过标准仍须明确。Web／PWA 的锁屏持续 IMU 没有本轮核实的保证，Capacitor Motion 当前使用 Web APIs；套壳不等于原生后台采集。原生方案同样需要目标设备实测。证据见 [调研 §4](research/tai3-models-and-platform-feasibility.md)。

### 后补后台能力的变更范围（工程建议，未验证）

可以后补，但不能保证改动很小或一定可行。建议从第一版就让采集 Module 输出明确时间语义、单位、坐标和缺测信息的记录；分析／仿真读取记录，而非直接依赖页面传感器事件。采集生命周期要能表达暂停、中断、恢复与停止，后台不可用时如实显示缺口。

如果从 Web 前台采集改为原生采集，可能要替换采集 Implementation，并新增权限、后台生命周期、安装／分发与能耗方面的工作。分析／仿真有望复用，但复用程度需要实现后验证。先在目标手机做范围受限的可行性验证，再判断首版一起做还是后补；验证预算与质量判据事先明确。无需预建多个空 Adapter，也不在此预选原生框架。

### 采集内容与质量（建议）

建议字段：
- 设备提供的原始时间戳及其时钟域，接收时间如另有记录则分别保存；含重力三轴加速度、三轴角速度。
- 可获得的姿态／重力估计，车速及其来源、时间与缺测标记；不能默认 GPS 或车辆总线永远可用。
- 设备／系统／浏览器版本、实际采样间隔、丢帧与间隙；约 100 Hz 或更高只是目标，不是保证值，也不代表能解析所有高频冲击。
- 模式、载荷、胎压、安装位置／朝向和固定方式等实验标签。

明确设备系、车身系与仿真系的映射、轴向、角速度单位和重力处理。手机固定牢靠；有重力与去重力信号分别标注。前台、切应用、锁屏测试先在安全静止场景验证连续性，再决定路测可行性。

可先以 phyphox 作真实数据导入验证途径，但同时采集配置、导出时间轴与实际频率要实测；不把第三方采集工具直接等同于本项目最终产品。

- <https://phyphox.org/experiment/gyroscope/>

## 5. 四类资料与本地优先（建议）

采集记录、车辆配置、校准结果、实验配置使用可关联的稳定 ID、版本、单位、坐标系和来源。JSON 配置、CSV 时序、ZIP 实验包是首版候选，不是已冻结的 schema。

- 原始数据不被派生数据覆盖；派生结果记录处理方法、参数、软件版本和输入引用。
- 仿真运行结果关联实验配置与求解器设置；有随机输入时记录种子。
- 跨设备导入／导出先于自动云同步；位置数据默认留本地。手机／电脑功能分工与存储容量尚待确认。
- 不提前设计账号后端、二进制全套格式、分布式同步或长期云服务。

## 6. 能解释什么，不能据此声称什么

- 手机是车身安装点的**响应输出**，不是路面输入。未知路面加单手机通常不足以唯一识别真实悬架参数。
- 使用同位置／朝向的虚拟手机比较，并处理转动引起的安装点加速度、重力和坐标变换；不能只拿车身质心加速度直接对齐实物。
- 不用加速度直接双积分声称恢复了可靠悬架行程。参数拟合必须写明输入假设、可辨识范围、误差与非唯一性。
- 建议首版聚焦低频车身响应；不承诺尖锐冲击、轮胎高频变形、人体／座椅／物品动力学、极限操控或原厂云辇控制律复现。
- `f = V / λ` 对周期空间起伏有解释力，单一减速带是宽频输入；不能从单个速度阈值推出普适阻尼优劣。
